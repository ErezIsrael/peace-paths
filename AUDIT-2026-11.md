## 1. Findings — Cloudflare delivery

### 1.1 `data.json` is uncacheable and burns KV reads on every view
`functions/data.json.js` returns `Cache-Control: no-cache, no-store, must-revalidate`, so every page view = 1 Pages-Function invocation + 1 KV read.
Free plan limits: **Workers/Pages Functions 100 000 requests/day** and **KV 100 000 reads/day** — one viral Reddit/WhatsApp share (this is a shareable site) saturates both, and every visit pays function + origin latency for a document that changes 10×/day.

**Fix (small):** cache it. In the function: `env.peace_data.get("data.json", { cacheTtl: 60 })` (KV minimum TTL is 30 s) and respond with
`Cache-Control: public, max-age=0, s-maxage=120, stale-while-revalidate=600` (or `CF-CDN-Cache-Control`). The 15-min client auto-refresh stays exactly as-is; you collapse ~100k reads/day into ~700.

### 1.2 No fallback, and the fallback that exists is broken
`loadData()` falls back to `./solutions.json`, but that file is gitignored → not deployed → the URL returns **200 with `text/html`** (Pages 404→index fallback), so `res.json()` throws and the UI shows "Failed to load data". `app/_headers` still carries a dead `/solutions.json` rule.

**Fix:** make the function fall back through KV snapshots (`data.json` → newest `data-<date>.json`), and delete the dead fallback + `_headers` rule.

### 1.3 No versioning / rollback of the published data
The pipeline writes one KV key. A bad run (bad narrative, bad phase, empty day) is instantly live with no undo. Snapshots cost nothing: `data-2026-11-27.json`, `data-2026-W48.json` → rollback becomes a two-key swap and unlocks a *history/timeline UI* (you already generate the content for it — see §4.6).

### 1.4 Stale-data blindness
If the KV upload fails (it retries 3× then gives up) or a timer fails, the site keeps serving old data with **no indication at all**. The frontend already trusts `data.aiHealth`. Publish a `health.json` (last run, duration, feed errors, counts) and show a "⚠️ data is 14 h old" banner.

## 2. Findings — payload & front-end performance

### 2.1 The font is the site
`app/fonts/inter-variable.ttf` = **874 KB on disk, 445 KB transferred**, containing Latin + Greek + Cyrillic + Vietnamese subsets the site never renders. No `preload`, no `unicode-range` splitting, TTF not WOFF2.
→ Subset to **hebrew + latin + arabic** WOFF2 with `unicode-range`, `preload` the Hebrew one. Expect 445 KB → ~100 KB and LCP ~3.1 s → ~1.2 s. Same treatment for `space-grotesk-variable.ttf` (134 KB), or drop it — a peace tracker does not need two display faces.

### 2.2 ~40% of `data.json` is never read by the frontend
Byte analysis of the live payload (375 KB):

| Field(s) | Bytes | Used by `app.js`? |
|---|---|---|
| `events[].snippet` | **86.5 KB** | **no** (0 references) |
| `narrative.weeklyHistory` | **36.4 KB** | **no** |
| `narrative.keyEvents` + `keyOpinions` | 23.0 KB | yes |
| `narrative.milestones` | **10.0 KB** | **no** |
| `cluster_size`, `ai_risk`, `source_weight` | 7.6 KB | **no** |

Pruning to exactly what the UI consumes: **396 KB → 200 KB** (before even disabling `indent=2`, which is a free 17%: the file uploaded to KV is pretty-printed).

Better still, **split the payload**: `data.json` = card-level (narratives + top 10 events/solution, ~90 KB), `events-<solutionId>.json` fetched on demand when a card's event layer is expanded. Users get the story in a third of the bytes.

### 2.3 Boot waterfall
`boot()` does `await loadTranslations()` before `loadData()`. translations.json is static — either inline it into `app.js` (it's 23 KB, and versioned together) or `Promise.all` the two fetches, and add `<link rel="preload" as="fetch" crossorigin href="/data.json">`. Also: 3 s of blank page — render the localized shell immediately, then fill.

### 2.4 Cache headers on assets
`app.js` is `max-age=300` but the HTML requests `app.js?v=0.5.19` while `APP_VERSION` is `v0.5.20` — the version string is maintained in two places and already drifted. Content-hash the assets (or bump both from one place) and give them `max-age=31536000, immutable`; `translations.json` gets long caching too.

## 3. Findings — front-end design, UX, accessibility

### 3.1 The story is collapsed away by default
Every card ships 4 narrative layers and **12 of them start collapsed**; the long-term narrative — the actual product — is hidden behind a click on 9–10 px text. There is no "expand all", no deep link, no per-solution URL.
Recommend: `longTerm` + `weeklyHighlight` open by default, `keyEvents`/`keyOpinions` collapsed; `#/<solution-id>` hash routing so cards are shareable (and indexable).

### 3.2 Keyboard users cannot use the site
All 13 collapsible toggles are `<div>`s with `onclick` → **0 focusable**. Five "links" are `<a href="#">` (privacy, terms, accessibility, how-it-noops, logo). No skip link, no `aria-live` for the silent 15-min re-render, no `aria-expanded`. For an Israeli public-interest site this is also a policy exposure.
Fix: emit `<button class="…collapsible-toggle" aria-expanded="false">`, give card titles `h2`, wrap the grid in `aria-live="polite"`.

### 3.3 Dark theme fails contrast at small sizes (measured, alpha-composited)
`--text-dim:#5a7a9a` on `--card:#132a4a` = **3.2:1**; 13 failing pairs, all at 9–11 px: layer titles (3.09), direction badges (3.65/3.70), phase labels (3.21 at 9 px), attestation count (2.72), "how it works" (4.04). Light theme passes.
Fix: `--text-dim` → ~`#8fa9c4` (≥4.5), and raise the floor from 9 px to 12 px; 9–10 px body copy on a phone is the real reason the cards feel dense.

### 3.4 Language polish on the default Hebrew UI
- `formatTime()` hardcodes `m ago` / `h ago` / `d ago` → the Hebrew page literally shows "עדכון אחרון 7m ago". Add `minutesAgo/hoursAgo/daysAgo` translation keys (or `Intl.RelativeTimeFormat`).
- `index.html` is `lang="he" dir="rtl"` but every static string is English until JS runs → English flash on first paint. Use `data-i18n` attributes with Hebrew in the HTML.
- Solution names/phases from `categories.json` render as English in RTL cards when a translation is missing (`Google News - Lebanon`, stakeholder names). Either translate stakeholder names in the pipeline or mark them `dir="ltr"`.
- The frontend's `sanitizeText()` contains a JSON-array-repair path — that is the UI compensating for the LLM returning `["text"]` instead of a string. Fix at the source (§4.5) and keep the guard as belt-and-braces.

### 3.5 What's missing as a product
- **No social preview**: no OG image, no `og:description`, no Twitter card. A tracker meant to be forwarded renders as a bare URL in WhatsApp/X. Highest-leverage 30 minutes of design work on the whole site.
- **Trust signal is computed but never shown**: you have `source-profiles.json` (92 outlets with `lean`/`region`), `attestations`, and `cross_attestation_bonus` in the payload — the UI shows "1 מקורות" and nothing about lean. "Reported by 3 sources across the ideological spectrum" is your differentiator; put it on the card.
- **No archive/history**: `milestones` + `weeklyHistory` are generated daily and shipped to every visitor, and nothing renders them. A "this month in peace efforts" panel costs one render function.
- **No SEO surface**: content is JS-rendered behind an uncacheable `fetch`; no sitemap, no `hreflang`, no structured data. A Pages Function could serve a prerendered HTML summary to crawlers (or just emit the top-of-card text server-side).
- Minor: no PWA manifest (mobile-first Hebrew audience), no source/type filter, and IMEC is permanently invisible — it has a 10 KB narrative but 0 events, so `activeSolutions` filtering hides it forever.

## 4. Findings — AI pipeline (`ai-analyze-prod.py`)

### 4.1 RSS ingestion is the biggest hidden cost, and most of it is dead
Probe of all 89 feeds (2026-11-27):

- **3 HTTP errors:** Arab Organization for Human Rights (403), UNESCO Middle East (404), Jewish Chronicle (429 — every run)
- **8 reachable but zero items:** Middle East Eye, Walla, RFE–Farda, Independent–Iran, Independent–Gaza, Zochrot, Pardes, UNIFEM MENA
- **11 dormant >30 days:** Shatil (1 516 d), Middle East Institute (570 d), Alliance for ME Peace (525 d), IPD (494 d), Dignity/Kav LaOved (464 d), Google News–West Bank (79 d), Reuters ME (50 d), BBC–Iraq (45 d), BBC–Lebanon (41 d), Near East Foundation (38 d), Freedom Flotilla (35 d)
- **2 silently dropped for unparseable dates:** Crisis Group, PNN (feed is alive, pipeline throws the items away)
- **19 of 89 feeds produced anything in the last daily run.**

Each fast run fetches ~560 items and discards 491 as too old, paying 5–8 failing connections every time. Meanwhile the footer claims "89 RSS feeds".

**Fixes:** prune the 11 dead + 11 dormant, fix the 2 date-parsing feeds (Atom `updated`/non-RFC822 dates), add conditional GET (`ETag`/`If-Modified-Since`) with a raw-response cache so re-classification doesn't require a re-fetch, track per-feed success/age in `staging/feed-health.json`, auto-disable a feed after N consecutive failures, and print an honest coverage number ("live today: 21 sources"). The 6 Google News query feeds are 429-prone and duplicate mainstream outlets — consolidate to 1–2.

### 4.2 Fast mode can silently lose the news it exists to catch
`--fast` fetches a hard **2-hour** window, the timer fires at 7,9,11…21 + 01:00 + 05:00 with `RandomizedDelaySec=10min`, and a run can be skipped by the lock or die on `TimeoutSec`. Any article published in a skipped/failed window is **unrecoverable until 02:00**.
**Fix:** widen the window (fast = 6 h) and keep a persistent store of seen article keys (`link` + normalized-title hash) so overlapping windows are cheap and loss-free. This is also the dedup table §4.3 needs.

### 4.3 Event clustering does nothing
`cluster_events()` → **137 clusters from 140 articles** (fast: 22/23). Jaccard on stop-word-stripped *title* tokens with a 0.65 threshold cannot match two outlets' headlines for the same event. Consequences: the activity feed repeats one event 3× under different sources, `keyMetric.value` ("83 events") overstates reality, and the narrative prompt spends tokens on duplicates.
**Fix (no LLM needed):** blocking (same solution + date ±48 h) → similarity over **snippet + title** using TF-IDF cosine or MinHash; entity overlap (place names) as the signal. Embeddings would be better but the router exposes no `/v1/embeddings` (verified: `{"error":"not found"}`) — a local `sentence-transformers`/TF-IDF pass on the server CPU is free and instant. Then verify: the run log should print a compression ratio like "140 → 95 events", and it should not be 1.0×.

### 4.4 The keyword short-circuit quietly decides a third of your "AI" output
Pass 1 accepts any article with ≥2 keyword hits and assigns `sentiment: neutral, type: reporting, signal_score: 5, risk: 5` **without any model call** — 98 of 270 articles on the daily run. Those defaults then feed `compute_direction()`, `effective_signal`, sorting and the momentum banner. So "Net Negative" is partly computed from hardcoded neutral.
**Fix:** let keywords *propose a category*, never *conclude sentiment/type/signal*; or shrink pass-1 acceptance to a high-precision rule set and stamp the payload with `"classified_by": "keyword"` so `aiHealth` reports it honestly and the momentum math can down-weight those events.

### 4.5 Batch classification is configured to truncate
`_batch_classify(..., batch_size=25)` sends 25 articles with **`max_tokens: 2000`** → ~80 tokens/article for a JSON object each. When it truncates, the fallback re-classifies all 25 one-at-a-time (25 sequential calls). The retry loop is good; the sizing is not.
**Fix:** set `max_tokens` proportional to batch size (or batch 10–12, which is what AGENTS.md already claims), and add `response_format: {"type":"json_object"}` to the **narrative**, **phases** and **translation** calls too — only the classifier batch uses it today, and `sanitizeText()`/`_repair_json()`/`_validate_and_fix_data()` exist to mop up exactly the artefacts that strict JSON prevents. Keep the "indices not text" trick in `generate_narratives()` — that part is genuinely clever and should stay.

### 4.6 Generated-but-unused narrative content
`milestones` and `weeklyHistory` are generated, translated, stored and shipped (46 KB/run) but never rendered. Either build the history view they were meant for, or keep them server-side only (in the weekly snapshot key) and stop shipping them.

### 4.7 Translation layer
Chunk-of-10 dual translation with script validation + single-item fallback is solid. Gaps: the cache is per-process (a restart re-translates), chunk boundaries split a 143-text day into 15 sequential calls, and `_translate()` (single, uncached on disk) is still reachable from `_make_trilingual()`. Persist the cache to `staging/translation-cache.json` (or a KV key) — translations are deterministic and never need re-doing.

### 4.8 Smaller pipeline items
- **Dead code in `main()`**: the fast-mode `_translate_events_to_trilingual(new_events_by_sol, [], …)` receives raw *article* dicts (key `title`, not `text`) → always prints "No texts to translate". Harmless, misleading; delete it.
- `upload_to_cloudflare(data)` ignores its `data` argument and re-reads `app/data.json` — a `--dry-run`/partial-failure path would upload a stale file. Pass the bytes.
- `app/data.json` and `app/solutions.json` are byte-identical 400 KB duplicates; one is enough.
- `determine_phases_ai` + 7 narrative calls are sequential with `sleep(15)` retries — fine on a single-slot router, but the narratives could be one call per 2–3 solutions to cut round-trips.
- **Journald timestamps are useless**: all 30 log lines of a run share one timestamp (block-buffered stdout). Add `-u`/`PYTHONUNBUFFERED=1` to the unit — the admin "Server tab" log stream depends on this.
- Tunables (`MAX_ARTICLES_PER_FEED=8`, `MAX_AGE_DAYS=7`, `LOCK_*`, batch size) should be CLI flags/env, not constants.
- **Zero tests.** Add a `--fixture` mode (a frozen `staging/articles.json`), assert the output schema, assert "every rendered field is non-empty in en/he/ar", and assert `clusters < articles`. That's a 20-minute GitHub Action that runs on the laptop, not the GPU server.

## 5. Findings — data, config & ops drift (this one will bite you)

Three different versions of the pipeline exist:

| Copy | `ai-analyze-prod.py` | `prompts.json` | `categories.json` |
|---|---|---|---|
| repo HEAD | `1843930…` | `18301e3…` | — (gitignored) |
| laptop working tree | `1b292bc…` **(uncommitted)** | `e96458d…` **(uncommitted)** | `0b566c6…` |
| AI server (what actually builds the site) | `46d2078…` (= working tree, minus the IP scrub) | `e96458d…` | **`5d6dc6c…` (differs from laptop)** |

- The prompt/narrative work in the laptop working tree is **uncommitted** but **live on the server** — no history, no rollback, easy to lose.
- `categories.json` — the taxonomy the entire site depends on — **differs between laptop and server, is gitignored, and exists nowhere else**. Same for `rss-feeds.json` and `.env`. One disk event on the server and the site's brain is gone.
- Deploys are manual `scp` per AGENTS.md; nothing verifies the server matches the repo.

**Fix:**
1. Commit the working-tree changes now.
2. Split gitignored-but-precious config into **`config/` committed** (`categories.json`, `rss-feeds.json`, `source-profiles.json`, `stakeholders.json`) and keep only secrets in `.env` (which also has a stray `CLOUDFLARE_API_TOKEN1` typo). Redact nothing — these aren't secrets, they're the product.
3. Make the server a git checkout: `ExecStartPre=/usr/bin/git -C /home/erez/peace-paths pull --ff-only`, and add `--pipeline-version` to `data.json` so the live site tells you which code produced it.
4. Nightly GitHub Action: `wrangler kv key get data.json` → validate schema → commit a dated copy to a `snapshots` branch. Belt-and-braces backup with zero moving parts.
5. AGENTS.md has drifted from reality: 75 vs 89 feeds, "every hour" vs every 2 h, "batch LLM (size 10)" vs 25, model default `Qwen3.6-27B` vs `Qwen3.6-27B-IQ4_NL.gguf`, profile list missing `strata` (currently active), "KV upload via `npx wrangler`" while production uses the REST API in Python.

### Repo hygiene
`test/` and `dev-environment/` are full copies of `app/` (three copies of `app.js`, `styles.css`, `translations.json`; dev `app.js` is already 7 KB behind prod). Collapse to one `app/` plus a dev server flag that chooses the data source. Root also carries decommissioned Windows task scripts, `ai-analyze.py`, `dev-serve.py`, `check-phases.py`, `nul`, a 27 KB file literally named `-w`, `temp/`, `screenshots/`, and two stale planning docs (`MIGRATION-PLAN.md`, `EVENTS_PLAYERS_PLAN.md`) — some are gitignored, but they make the tree hard to reason about.

## 6. Target architecture (what I'd converge on)

```
                        ┌── feed-health.json (per-feed status, auto-disable)
75-90 live feeds ──────►┤   conditional GET + raw cache (staging/raw/)
                        └──► seen-keys store (link+title hash)  ← overlap-safe windows
                                    │
              keyword PRIOR (category hint only)
                                    │
              batch LLM: category + sentiment + type + signal  (json_object, sized max_tokens)
                                    │
              blocking + TF-IDF/MinHash event resolution  (140 → ~90 events)
                                    │
        ┌── phases ──┬── narratives (indices, not text) ──┬── shifts
        └────────────┴───────────────────────────────────┘
                                    │
                persistent translation cache  (never re-translate)
                                    │
        ┌─ data.json         slim, card-level      (~90 KB, compact)
KV ─────┼─ events/<sol>.json lazy                  (fetched on card expand)
        ├─ history/<week>.json milestones+weeklyHistory  (new archive UI)
        ├─ data-<date>.json  snapshot / rollback
        └─ health.json       run status → staleness banner + admin panel
                                    │
        Pages Function: KV get {cacheTtl:60} → s-maxage:120, swr:600
                        fallback chain: current → newest snapshot → 503
```

Front end: one `app/` tree, shell painted instantly in Hebrew, WOFF2-subset fonts preloaded, `data.json` preloaded in parallel with inline translations, cards open on their narrative, hash-permalink per solution, OG image, `events-<sol>.json` lazy-loaded, all toggles `<button aria-expanded>`, 12 px text floor, `--text-dim` ≥ 4.5:1.

## 8. Keep as-is (deliberately good design)

- Lock file + heartbeat + fast-waits-for-daily + stale-lock takeover — genuinely thoughtful concurrency design for a shared single-slot GPU.
- `generate_narratives()` referencing events **by index** and re-attaching metadata in code — the right way to stop an LLM inventing citations.
- Trilingual `{en,he,ar}` schema end to end, and domain glossaries in `_batch_translate_dual`.
- `source-profiles.json` bias tagging, `effective_signal`, cross-attestation bonus — the modelling instinct is right; it just needs to reach the UI.
- `staging/*.json` per-stage dumps — cheap, and they made this audit possible.
- `aiHealth` surfacing refusals and keyword fallback to the browser instead of hiding them.
- Keeping the site static + KV, updates on the server, laptop off: correct architecture. The fixes above are inside that architecture, not a rewrite of it.

Three findings that surfaced only after shipping:

1. **Pages Function responses are not CDN-cached on this plan — measured, not assumed.**
   A temporary probe branch in `functions/data.json.js` returned `Date.now()` for a fixed
   URL; five samples 20 s apart inside the `s-maxage=120` window each came back with a new
   timestamp and a different isolate id → the Function runs on every request. Cloudflare
   echoes `CF-CDN-Cache-Control` but does not honour it without Cache Rules (a paid/enterprise
   feature). What still holds: KV `cacheTtl: 60` means the *value* is edge-cached, so a page
   view is not an origin KV read. Function invocations remain 1 per page view (free tier:
   100 000/day — not a risk at this site's traffic, but stop assuming −99% there).

2. **Dormant solutions were paid for but never shown — fixed in v0.7.0.** `activeSolutions`
   only contains solutions with events in the current window, so a solution with full narrative
   memory (`abraham-accords`, `i2e2c`) disappeared from the grid while still costing **14.9 KB —
   9.7% of the payload**. Now rendered as a "quiet tracks" section under the grid: one collapsed
   `<button aria-expanded>` row per dormant solution (icon, name, "no new developments" pill,
   last activity date) whose panel reuses `buildLayeredCard`, so the long-term arc, weekly
   highlight and archived key events are finally readable. That is the display half of item 18.
   **New consequence:** dormant entries now have a real consumer, so their growth matters — the
   daily keeps inactive solutions indefinitely (2 of 7 categories today). When that grows, cap it
   by last-activity age or move the archive into lazy `events/<sol>.json` files (item 18) instead
   of letting `data.json` swell again.
3. **Translation is now the slow stage of a fast run** — 27 texts took 102 s of the 129 s run
   (~3.8 s/text when the router is also serving this agent). Item 16 (persistent translation
   cache) is now the top P1 item by wall-clock payoff.
4. **Section labels are buttons, not headings.** The three section labels (activity feed,
   solutions, quiet tracks) are `section-header` divs/buttons — keyboard-operable, but a
   screen-reader user cannot navigate by heading the way the card `h2`s allow. One pass when
   touching layout: wrap each label in an `h2`/`h3` around the button.

Not yet done from P0: none. Start P1 at item 11 (seen-key store + 6 h fast window) and 16
(translation cache); item 12 (event resolution) still shows 31 clusters from 34 articles.

### Automation note for whoever audits next

`app/_headers` ships `Content-Security-Policy: default-src 'self'; script-src 'self'`, and the
site has no inline scripts — correct, but it means Playwright's `wait_for_function()` and any
in-page `eval` are blocked (`unsafe-eval`). Use `wait_for_selector()` instead. Verified CSP-safe:
one external `app.js?v=…`, no inline handlers, no `eval`/`new Function`/`document.write` in
`app.js`. Adding an inline snippet or analytics tag needs a hash/nonce plan first.

Where the audit was wrong, corrected in place:

- **Item 12 predicted "dedup 1.0× → ~1.5×". The corpus says otherwise.** In a 266-article /
  48 h fixture, cross-feed duplication is about 2% of articles. The old rule was not
  under-merging because of a weak metric so much as because there is little verbatim
  duplication to catch; the new metric (IDF over title+snippet, entity gate, headline-subset
  rule) is a strict superset of it, which is the honest claim. `tools/check-clustering.py`
  prints old-vs-new groups so this is re-checkable rather than asserted.
- **The translation bottleneck was worse than "~15 calls/run"**: translation was 102 s of a
  129 s run, i.e. ~80% of wall clock. The cache plus the seen-store means a typical hourly run
  now spends under 10 s total, and the LLM pressure the audit worried about is largely gone.
- **Batch classification was not truncating, it was answering the wrong question**: the
  function reused the single-article system prompt under `response_format: json_object`, so the
  model returned one classification object for the whole batch. `max_tokens` sizing (item 14)
  was only half of it — the prompt contract was the real bug.

Runtime state added by these changes (all under `.state/`, gitignored, server-owned):
`.state/translation-cache.json`, `.state/seen.json`. They are cache/memory, not configuration:
deleting them costs time, not data — but the seen store is what keeps a fast run from
re-classifying, so treat a wiped `.state/` on the server as a cold start.

## 12. Two pipeline bugs found only after the P1 items landed (2026-11-27)

Both were visible only because the caches made runs fast and frequent enough to compare
run *N* against run *N+1*.

**1. Every run deleted one event per solution (`7852a` "stop eating one event").**
Both the build path and the merge path did `events = events[1:]` right after copying that
event's text into `summary` — a display convention from an older design. `summary` is not
read by the frontend at all (the card headline comes from the narrative; the momentum
banner from `overallMomentum`), so the pop was pure loss. Measured on the live payload
across consecutive fast runs:

| solution | before | after |
|---|---|---|
| iran-us-peace-process | 97 | 96 |
| 20-point-gaza-peace-plan | 68 | 67 |
| geneva-initiative | 18 | 17 |
| west-bank annexation | 11 | 10 |
| lebanon-hezbollah | 3 | 2 |
| abraham-accords | 1 | **0** (silently became a quiet track) |

≈1 event per solution per fast run, 10 fast runs/day, and `keyMetric` ("N events")
disagreed with the array the browser received by one. After the fix the same comparison
shows one solution +1 (its genuinely new event) and none −1. Events already eaten and
older than the 7-day feed window are unrecoverable.

**2. A quiet window was misdiagnosed as an AI failure (item 13 follow-up).**
`if not classified_pairs:` triggered the keyword fallback, so on a window where the model
correctly judged everything irrelevant the pipeline (a) re-inserted the keyword verdicts
item 13 had just removed and (b) published `classificationMethod: "keyword-fallback"`,
which switches on the warning banner in the live UI. Now `classify_articles` returns
`llm_answered` and the fallback requires `not classified_pairs and llm_answered == 0`.
Fixture probe: 3 articles, all dropped → `llm_answered=3`, old trigger `True`, new trigger
`False`.

Lesson for the next audit: instrument runs so consecutive-run diffs are readable
(`publishing … (local data.json is …)`, per-solution `eventCount`, `aiHealth.classifiedBy`).
Both of these were invisible in a single run's log.

## 13. Content quality — measured, then fixed (2026-11-28)

Performance work made runs cheap; that made the *content* worth measuring. `tools/eval-content.py`
now scores the published output (scope, redundancy, text hygiene, and whether the numbers on the
card mean anything), with `tests/fixtures/published-events-2026-11-28.json` — all 199 events that
were live that morning — as the baseline fixture.

The scope pass uses the model as annotator against each tracker's own `description` from
`categories.json`, i.e. exactly the text the classifier is given. Two readings are reported because
they bracket the truth: **strict** (initiative only) and **moderate** (initiative + developments
that change its odds). Temperature 0 still moves ±2 points between runs; single-digit differences
are noise.

### What was wrong

1. **Trackers were topic buckets, not initiative buckets.** The `geneva-initiative` ("Two-State
   Solution") archive of 28 events was: 11 stories about a UN rapporteur stuck at a Costa Rica
   airport, 8 about Israeli coalition talks, one Vietnamese two-state statement, a Myanmar
   genocide-verdict op-ed, Netanyahu's corruption case, a blog link roundup — **zero about the
   Geneva Initiative or its Two-State Index**. `abraham-accords`: an Iranian tennis player refusing
   an Israeli opponent, OPEC politics, a Turkey op-ed.
   It was live, not legacy: replaying those headlines through the classifier reproduced
   `geneva-initiative` **8 times out of 8**. The mechanism: broad descriptions ("…diplomatic
   efforts by Saudi Arabia, France, and the UN") plus `_make_classifier_prompt` injecting
   `[Context: Phase: … Recent: <last 3 headlines>]`, so a mislabelled bucket recruited more of the
   same. The drift was self-reinforcing.
2. **One development, many events.** `_merge_with_existing` deduped on the exact English headline.
   9% of published rows were repeat coverage; only **6 of 199 events carried a second source**, so
   the cross-attestation feature the UI was built for never fired.
3. **Publisher chrome as content**: 32 rows ended in ` - Outlet`, 8 began with `Iran war live:` /
   `Watch:` / `Opinion |`, 3 were link digests (`11/26 Links Pt1: Melanie Phillips…`), 1 a TV ticker
   (`PTV. . #PTVNewsTonight | …`).
4. **Numbers that measured feed depth**: `keyMetric` was the row count (63 vs 7 = how much those
   feeds publish); `confidence` was `len(events) > 5` → "high" for all seven trackers, including one
   whose six events were five-and-a-half off topic.
5. **Direction was sentiment arithmetic over war coverage** (75% negative), so every tracker read
   "stalling" on every run and the momentum banner never moved.
6. **A log line inside the editorial text**: `shifts` carried the machine-translated sentence
   "Phase changed: Infrastructure Financing and Construction to Feasibility Studies and Route
   Mapping" — which is how IMEC could display "advancing" while its phase moved *backwards*.
7. **UI regression found while fixing this**: since the payload split every card read
   `2 אירועים`, because the header count came from the two inline events while `keyMetric` said 63
   and the archive said 98.

### The decision that shaped the fix

The user was asked and answered: **war escalation counts as content for a peace tracker.** So
escalation is kept — but labelled. Every event now carries `tier`: `initiative` (the
initiative/process itself) or `context` (the surrounding war and politics that change its odds).
Keyword-only judgements and fallbacks are always `context`; nothing can be counted as initiative
progress without a model judgement.

### Before → after (same tool, same fixture for "before")

| measure | before | after |
|---|---|---|
| published events | 199 | **117** (−41%) |
| in scope, moderate reading | 65% (129/199) | **66%** (77/117) |
| in scope, strict reading | 19% (37/199) | **35%** (41/117) |
| worst tracker: geneva-initiative | 14% (4/28) | **67%** (4/6) |
| worst tracker: abraham-accords | 33% (2/6) | **100%** (2/2) |
| repeat rows (loose 0.40 similarity) | 9% (17/199) | **4%** (5/117) |
| live blogs / roundups / tickers | 12 | **0** |
| outlet-suffixed titles | 32 (16%) | 16 (14%) — the rest are outlets we don't know |
| momentum spread | 1 advancing / 0 stable / 6 stalling | **2 / 2 / 3** |
| confidence spread | all seven "high" | 2 high, 4 medium, **1 low** |
| tiers | none | 21 `initiative` / 96 `context` |
| attestation reach (offline replay of the old archive) | 6 of 199 events | **11 of 188** after resolution |

Honest caveats: the moderate-reading score barely moved (65% → 66%) because the fix's first effect
was to *delete* off-topic rows rather than to classify the same corpus better — event volume fell
41% while the in-scope share of what remained went up, and the strict reading rose 19% → 35%.
Residual redundancy is ~4%: pairs like "US military repelled drones at UK airbase" vs "U.S. forces
repelled drones nearing British airbase" sit below the 0.55 merge threshold, and 0.45 starts merging
genuinely different events (measured: it merged two distinct two-state diplomacy items). The
threshold was set from both directions, not guessed.
